# Supervisor message templates

The messages the supervisor sends to builders, reviewers, PRs and the owner. Each template comes from messages actually sent between 2026-09-30 22:00 and 2026-10-01 08:15 UTC. Times without a date are 10-01. The real texts came from the supervisor's `create_session`, `create_trigger`, `add_issue_comment` and `create_pull_request` calls, and from its chat replies.

This file holds only the message texts. The rest lives in these files:
- what a session's fields mean, and what a builder or reviewer prompt must contain: `HANDOVER.md` 6.1;
- how to message a running session: `HANDOVER.md` 6.2;
- the review rules: `HANDOVER.md` 5.5; the merge steps: 6.8; the APK steps: 6.9;
- writing a card and checking it for collisions: `.claude/skills/supervisor/cards.md`;
- the APK steps in short: `.claude/skills/supervisor/ship-apk.md` (its quoted message format is older; send the text in 10a below);
- what builders and reviewers do on their side: `.claude/skills/builder/SKILL.md`, `.claude/skills/reviewer/SKILL.md`;
- incidents and their rules: `HANDOVER.md` section 9 and `.claude/skills/supervisor/gotchas.md`.

## 0. Rules for every message

- **Build the text in a file with Python, then read it back.** Before sending, run `grep -n '<' msg.txt`. Every hit must be a marker the agent fills in itself, such as `<full sha from git rev-parse HEAD>` or `<side>`; any other `<…>` is a placeholder you forgot to fill. HANDOVER section 9 explains why.
- **SHAs.** Read them live; never copy one from a comment:
  - a PR head: `git ls-remote origin refs/pull/<PR>/head`;
  - a branch: `git rev-parse origin/<branch>`.
  - Write the full 40-character SHA wherever a tool or a reviewer acts on it, and 7 characters in headings.
  - Today two corrections had to follow: AUD-1 at 01:23 (the head did not contain the latest main) and AUD-11 at 05:55 (a wrong full SHA, copied from a FIXED comment).
- **Never put these in a message:** secrets, tokens, the Relay URL, email addresses or phone numbers.
- **Drop the old line "The account is near its weekly usage limit: work lean, no sub-agents."** The owner said at 08:10 not to throttle for usage. AGENTS.md's token rules still apply.
- **The comment footer.** Every GitHub comment, whether the supervisor posts it or tells an agent to post it, ends with a blank line, then `---`, then `_Generated by [Claude Code](https://claude.ai/code)_`.
- **Start your own PR comments with `**Supervisor`.** `monitor.sh` skips those comments (HANDOVER 6.5).
- **Session ids.** `<SUP_SESSION>` is your own session id; `get_session` with no arguments returns it. `<TARGET_SESSION>` is the session you are messaging. Find it in the HANDOVER 8.3 table or with `list_sessions`.

### Fields for every message to a running session (`create_trigger`)

| Field | Value |
|---|---|
| `persistent_session_id` | `<TARGET_SESSION>` |
| `run_once_at` | 2 minutes ahead, worked out right before the call: `date -u -d '+2 minutes' +%Y-%m-%dT%H:%M:00Z`. It must be in the future. On 09-30 at 23:33 one was sent for 23:25 and had to be sent again. |
| `initiation` | `own_followup` |
| `name` | Short: `<CARD> <what>`, for example "AUD-4 delta review 21a8d9a". |
| `prompt` | The message. |

Afterwards, check that it fired: `get_trigger` → `last_run`. If it did not fire, post the same text on the PR. Never use `fire_trigger` with text, because that starts a new, empty session.

### Fields for every new session (`create_session`)

| Field | Builder | Reviewer |
|---|---|---|
| `title` | `Builder: <CARD> <short name>` | `Reviewer: PR #<PR> <CARD> <short name>` |
| `model` | `claude-opus-5-5`. Use `claude-sonnet-5` only when every step is spelled out (today: AUD-5, AUD-11, AUD-12 and the COPY-1 fixer). | Always `claude-opus-5-5` |
| `permission_mode` | `auto` | `auto` |
| `source_url` | `https://github.com/macdarenz-droid/M-arc` | same |
| `source_revision` | Leave it out for a new card (it starts from main). Set it to the card's branch for a replacement, resume or fixer. | The PR's branch |
| `outcome_branch` | New card: not set (the prompt names `claude/<slug>`). Replacement, resume or fixer: set it to the card's existing branch, the same value as `source_revision`; otherwise the new session pushes to a new branch and the open PR never moves (HANDOVER 6.1). The HT-9 Opus builder of 08:38 was started this way. | Not set |
| `tags` | `["marc:builder","marc:<card>"]` | `["marc:reviewer","marc:<card>"]` |
| `environment_id` | Leave it out (it inherits). | Leave it out |

`<card>` in tags is the card in lower case, for example `marc:aud-20`.

## 1. Builder start

**When.** A card is `ready`: it passed the collision check in `cards.md`, and its lane has a free slot. Lanes build in parallel (all AUD cards ran at once). Merges still follow the checklist order.

**Call.** `create_session` with the builder column above.

```text
You are the BUILDER for card <CARD> in macdarenz-droid/M-arc. Your supervisor is <SUP_SESSION>. Follow AGENTS.md and .claude/skills/builder/SKILL.md, in auto mode. Do not use scheduling tools.

Card <CARD>: <TITLE>. <Either the full card text, or: Read "<exact heading>" in <file/comment> on <branch/PR>; read only those sections.> Line numbers may have moved, so re-check every cited line on origin/main.
<Owner rules or accepted defaults that apply, quoted with date.>

Do:
1. <step>
2. <step>
write_scope: <paths>.
Out of scope: <the How-to sheet (golden B) | the watch agent's files | escobar-worker/** | Play-required copy | other cards' files>.

Evidence:
- Each acceptance item has a unit test or gate probe that fails on main and passes after. Show both.
- Nothing is loosened. Gate blocks are add-only. No new saved data.
- Record decisions as D-<CARD>-* in docs/COACHING-DECISIONS.md.
Collision: <OTHER_CARD> (#<PR>, <state>) edits <file>. When it merges, merge origin/main and keep its logic.
<Hard card only: Post a design-note CHECK-IN on the PR before bulk building.>

Base: origin/main (<MAIN_SHA7> or later). Branch: claude/<slug>. After the first push, open a draft PR "<CARD>: <title>" that maps each acceptance item to its evidence.
Verify: npm ci; npm run check; npm run test:tz; MARC_CHROMIUM=/opt/pw-browsers/chromium npm run gate. Merge origin/main (merge commit) before asking for review. When everything is green, put "[ready for review]" at the start of the title and post "<CARD> READY: <full sha from git rev-parse HEAD>" on the PR, ending with a blank line, ---, _Generated by [Claude Code](https://claude.ai/code)_. Then stop; a reviewer follows. Don't wait for CI's android-gate. If anything needs a judgement the card does not settle, ask on the PR and stop.
```

**Variant: partial head.** Use it when part of the card waits on another PR. Post `<CARD> PARTIAL: <full sha>` and wait for my message. The partial head is reviewed early (COPY-2, 06:43).

**Variant: replacement builder.** Use it when the card's builder session is archived or lost (a stalled builder, a model swap such as HT-9 at 08:38, or an account switch). Set `source_revision` and `outcome_branch` to the card's branch. Add to the prompt:

```text

```

## 2. Reviewer start

**When.** As soon as `<CARD> READY: <sha>` or `<CARD> PARTIAL: <sha>` appears (a `monitor.sh` line). Start one fresh Opus reviewer per card. Keep it until the card's final PASS, because every delta review goes to the same reviewer. Then archive it, after checking `post_turn_summary` and the posted verdict.

**Call.** `create_session` with the reviewer column above. Confirm the head with `git ls-remote` first.

```text
You are the REVIEWER for PR #<PR> (<CARD>) in macdarenz-droid/M-arc, at head <FULL_SHA>. Confirm the head with `git ls-remote origin refs/pull/<PR>/head`. Your supervisor is <SUP_SESSION>. Follow AGENTS.md and .claude/skills/reviewer/SKILL.md, in auto mode. Do not use scheduling tools. Never use /ultrareview.

The card (from the supervisor) is <CARD>: <title>.
<Restate the card in full: owner rules or defaults, write_scope, out of scope, acceptance items. Never "see the PR".>

Check these specially:
1. Scope: run `git diff --stat origin/main...<SHA7>` (3-dot). For each file outside write_scope, judge whether the card needs it. <Name the owner-approved files, such as models.ts: no new kind of saved data.>
2. Every acceptance item has evidence. Its test fails on main and passes on this head. Prove the tests bite by mutation: <name the mutation, for example "revert <change> in <file> and show <test> fails">.
3. Nothing is loosened. Gate blocks are add-only. Pins updated to new strings check the same thing as before.
4. <Card-specific risks: privacy redaction, IDs verified at the source, the copy rule, golden fidelity (L3 at 0 px)>.
5. The head contains the latest main. Being behind main is a note, not a blocker.

Run npm ci, npm run check, npm run test:tz and MARC_CHROMIUM=/opt/pw-browsers/chromium npm run gate.

Post your verdict on #<PR> as "## REVIEW <CARD> @ <SHA7>: PASS|FAIL". Include Blockers/High/Medium/Low counts, findings with file:line and a fix, a criteria table (criterion, evidence, result) and the commands you ran. Use a PASS heading only when nothing is blocking. End the comment with a blank line, ---, _Generated by [Claude Code](https://claude.ai/code)_. Push nothing, then stop.
```

The heading `PASS|FAIL` is what reviewers post in practice. The reviewer skill still says `PASS | CHANGES NEEDED` (HANDOVER 7.6 item 10). Read both as verdicts.

> Post your verdict on #162 as "## REVIEW AUD-20 @ e8a0e9c: PASS|FAIL". […] Use a PASS heading only when nothing is blocking. […] Push nothing, then stop.

## 3. Delta review

**When.** Send one of these to the **same** reviewer session:
- the builder posts `<CARD> FIXED: <sha>` after a FAIL;
- the supervisor caught the branch up with its own merge commit;
- a defect fix lands after a PASS.

**Call.** `create_trigger` to the reviewer's session, named `<CARD> delta review <SHA7>`.

```text
Supervisor here. The <CARD> builder posted "<CARD> FIXED: <SHA7>" on #<PR> for your FAIL at <OLD_SHA7>. The full head is <FULL_SHA> (`git ls-remote origin refs/pull/<PR>/head`). Do a delta review of <SHA7>:
- <Finding 1, restated as what must now be true>
- <Finding 2 …>
- Nothing is loosened, and the whole diff (git diff --stat origin/main...<SHA7>) stays in scope.
Run npm run check, npm run test:tz and MARC_CHROMIUM=/opt/pw-browsers/chromium npm run gate on <SHA7>. Do not push. Post one comment on #<PR>, "## REVIEW <CARD> @ <SHA7>: PASS|FAIL", ending with a blank line, ---, _Generated by [Claude Code](https://claude.ai/code)_. Then stop.
```

**Variant: the supervisor's catch-up merge.** Replace the bullets with these:
1. The resolution is right on both sides.
2. No other file changed in the merge beyond main's own content.
3. Both cards' tests and gate blocks pass on `<MERGE_SHA7>`.

Add your local numbers ("typecheck 0, vitest <F> files / <T> passed"). Rule on the reviewer's Lows in the same message. (AUD-20 at 361c7fa, 07:09.)

**Variant: the fixes are inside a merge commit.** Tell the reviewer to diff the fix files against the pre-merge head, and to check the merge resolution separately (HANDOVER section 9, HT-8 `b2ab38c`).

**Real example (AUD-4, 03:37):**
> Supervisor here. The AUD-4 builder posted "AUD-4 FIXED: 21a8d9a" on #154 for your FAIL at dd6d501. Do a delta review of 21a8d9a:
> - Medium: AUD-2's branch is merged in, and tab B's fixture turns the coach on before sending. Only the fixture changed, and the full suite passes with AUD-2 in.
> - D-AUD4-1's wording is corrected.
> - active.entries has an entry {} with no exerciseId, and your mutation of the exerciseId filter back to objects() now fails.
> - […]
> - Nothing is loosened, and the whole diff (git diff --stat origin/main...21a8d9a) stays in scope.
> Run npm run check, npm run test:tz and MARC_CHROMIUM=/opt/pw-browsers/chromium npm run gate on 21a8d9a. Do not push. Post one comment on #154, "## REVIEW AUD-4 @ 21a8d9a: PASS|FAIL", ending with a blank line, ---, _Generated by [Claude Code](https://claude.ai/code)_. Then stop.

## 4. Fix after FAIL

**When.** A review or delta review posts FAIL.

**Call.** `create_trigger` to the builder's session, named `<CARD> review fixes`. Retitle the PR `[fixing] …` (HANDOVER 5.5). The reviewer's comment is already the record on the PR, so the trigger points to it by its heading.

Rule on every Low before sending: fix it now, it rides the next push, or it becomes a follow-up. Log each follow-up in the tracker for the improvement lane.

If the builder session is already archived, start a fixer instead: use template 1 with `source_revision` **and** `outcome_branch` set to the card's branch, plus the replacement variant. Example: the COPY-1 fixer at 09-30 23:14, on Sonnet because every step was spelled out.

```text
Supervisor: <CARD> review FAIL on #<PR> ("## REVIEW <CARD> @ <SHA7>: FAIL"): <N High, N Medium, N Low>. Read it, then fix:
1. <Severity>: <problem>. <Exact fix; which files it may touch; what stays unchanged.>
2. Low: <fix> | Low <n> stays out of this PR; I've logged it as a follow-up.
Each fix has a test that fails before and passes after. Show that the mutation <name> now fails. Nothing is loosened.
Then run npm run check, npm run test:tz and MARC_CHROMIUM=/opt/pw-browsers/chromium npm run gate, push, and post "<CARD> FIXED: <full sha from git rev-parse HEAD>" on #<PR>, ending with a blank line, ---, _Generated by [Claude Code](https://claude.ai/code)_. Then stop. Don't wait for CI's android-gate.
```

## 5. Freeze after PASS

**When.** The card's final PASS is posted. From then on, the supervisor merges the exact reviewed head through a merge train (template 9). Archive the reviewer after this.

**Call.** `create_trigger` to the builder's session, named `<CARD> passed, freeze head`.

```text
Supervisor: <CARD> passed <its review | its delta review> at <SHA7> (#<PR>). Freeze the head: push nothing more, and don't merge main. <The reviewer's Low (<what>) is optional and stays out of this PR; I've logged it as a follow-up.> I will merge #<PR> through merge train <N> <after <X> lands>. When the train merges, GitHub marks #<PR> merged. If your local checks on <SHA7> failed, post the failure on #<PR> instead of pushing a fix, and stop.
```

**Variant: hold during a review.** Use it when a reviewer is checking a partial head: "a reviewer is checking your PARTIAL head `<SHA7>` on #`<PR>`. Don't push while that review runs." Then queue extra items for the next push (COPY-2, 07:56).

**Real example (AUD-10, 04:55):**
> Supervisor: AUD-10 passed review at c8523d6 (#157). Freeze the head: push nothing more. The reviewer's Low (swappedFromToday keyed on today past midnight) is optional and stays out of this PR; I've logged it as a follow-up. I will merge #157 through a merge train after train 2 (AUD-1, AUD-4) lands, so you don't need to catch up with main. If your local checks on c8523d6 failed, post the failure on #157 instead of pushing a fix, and stop.

## 6. Catch-up ("X merged, merge main")

**When.** A PR merges that a running card collides with, or that comes before it in the lane order. Send this only to cards that are still building or fixing. A frozen, passed head is never told to merge main. If it conflicts with main, the supervisor catches it up itself with an attributed merge commit and sends a delta review (template 3, variant).

**Call.** `create_trigger` to the builder's session, named `<CARD>: <OTHER_CARD> merged, merge main`.

```text
Supervisor: <OTHER_CARD> (#<OTHER_PR>) merged to main at <MAIN_SHA7> (merge train <N>, #<TRAIN_PR>). <What it changed that matters to you: file, text or logic.> Merge origin/main into your branch with a merge commit now, and resolve any conflict keeping both sides (<OTHER_CARD>'s <logic> stays intact). Re-run npm run check, npm run test:tz and the gate on the merged head. Then <continue as instructed | post "<CARD> READY: <full sha from git rev-parse HEAD>" on #<PR>>.
```

**Real example (AUD-20, 05:08):**
> Supervisor: AUD-1 (and AUD-4) merged to main at b795f16 (merge train 2, #161). Before you post READY on #162, merge origin/main into your branch with a merge commit, resolve any conflict keeping both sides (AUD-1's recovery calibration and sleep floor stay intact), and re-run npm run check, test:tz and the gate on the merged head. Then post "AUD-20 READY: <sha>" on #162.

## 7. Supervisor ruling

**When.** A builder asks a question the card does not settle, or a review finding needs a choice between options.

**Steps:**
1. Post the ruling as a PR comment (`add_issue_comment` on the card's PR).
2. Send it to the builder as a trigger.

**Ruling id.** Use `D-<CARD>-<topic>`, for example `D-HT10-A5`. A later ruling on the same topic adds `-2`, `-3` and so on (`D-HT7-L3-text-2` … `-6`).

**Recording.** The builder records the ruling in `docs/COACHING-DECISIONS.md`. The supervisor adds it to HANDOVER 4.3. If the ruling changes drawn or pinned output, run the `cards.md` collision check (step 1) on that change first.

**PR comment:**

```text
**Supervisor ruling D-<CARD>-<ID> (<topic>).**

<The decision in one line.> <Why, with the measured data. Say plainly if a budget is re-set rather than loosened.>
- **Your part:** <the exact change, the files, the limits>.
- **My part:** <what the supervisor does itself, for example ".github wiring, add-only, in the same merge train">.
- **Evidence:** <the test or probe that fails before and passes after; the numbers to post>.
- Record it as D-<CARD>-<ID> in docs/COACHING-DECISIONS.md.

If the auto-mode classifier refuses an edit, stop and tell me. Never work around it.

---
_Generated by [Claude Code](https://claude.ai/code)_
```

**Trigger,** named `<CARD> ruling D-<CARD>-<ID>`:

```text
Supervisor: my ruling D-<CARD>-<ID> is on #<PR> ("<comment heading>"). Read it and follow it.
- <The 2-5 key points, short.>
<Keep going on the card. | Then run npm run check, test:tz and the full gate, and post "<CARD> READY: <full sha from git rev-parse HEAD>" on #<PR>.>
```

## 8. Defect routing

**When.** One card's sweep or review finds a defect in another card's code. Today HT-10's sweep found defects in HT-8 and HT-9. The card that found the defect never edits the other card's files.

**Steps:**
1. Verify the defect yourself: read the trace and the cited lines on main.
2. Post a short note on the owning card's PR.
3. Send the fix to the owning card's builder by trigger.
4. When FIXED lands, the owning card's reviewer does a delta review (template 3). If that reviewer is mid-review, tell it about the fix.

**Comment on the owning PR:**

```text
**Supervisor:** the <FINDER_CARD> builder found a defect in <OWNER_CARD>, reported on #<FINDER_PR>:

- <defect, one line>
- <defect, one line>

I've sent the fix to the <OWNER_CARD> builder. It stays in <OWNER_CARD>'s own files and adds a gate probe that fails before the fix and passes after. <OWNER_CARD> does not merge until that fix passes a delta review.

---
_Generated by [Claude Code](https://claude.ai/code)_
```

**Trigger,** named `<OWNER_CARD> defect: <short>`:

```text
Supervisor: the <FINDER_CARD> builder found a real <OWNER_CARD> defect. Read its comment on PR #<FINDER_PR> ("<comment heading>").
Summary: (1) <what fails, with file:line> (2) <the cause>.
Fix it in <OWNER_CARD>'s own files (<files>; no change to <OTHER_CARD>'s <file>). <If no other way: keep the change to one added selector, add a comment, and call it out in the PR.>
Add evidence that fails on <SHA7> and passes after: a gate probe in your <OWNER_CARD> block that <action and expected result, which themes>, plus a unit test where it fits.
Keep <the fidelity rules: L3 at 0 px, budgets measured + 10 %>. Nothing is loosened. Main is now <MAIN_SHA7>: merge origin/main (merge commit, keeping both sides) in the same push, and say so.
Run npm run check, test:tz and the gate, push, and post "<OWNER_CARD> FIXED: <full sha from git rev-parse HEAD>" on #<PR>.
```

**Real example (HT-8, 06:02): the comment on #111:**
