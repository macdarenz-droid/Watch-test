# HT-7 'Bony bump' root-cause workflow (wf_0d39b52a-1a0), judge synthesis, 2026-10-01 ~09:30 UTC

**HT-7 "Bony bump" width bug: ranked causes, tests and fixes**

**What I checked myself** (HT-7 head 75fd1a2, and Chromium 141.0.7390.37 source):
- `svg_layout_support.cc:48-67,367-379`: an SVG text's font size includes every ancestor PaintLayer transform. So the `.zx` scale(.9→1) zoom feeds into the label's font size.
- `layout_block.cc:137-190`: when an ancestor's scale changes, SVG text is only flagged. It is forced to re-lay out only if that block's stacking-context state flips. A null transform counts as scale² = 1 and an identity transform as 2.
- `layout_svg_inline_text.cc:68-90`: any style change resets the label's divisor (`scaling_factor_`). It re-lays out only when the change needs layout.
- `harfbuzz_font_data.h:43-49` and `harfbuzz_face.cc:636-655`: the SkFont and the HarfBuzz scale are rebuilt on every shape. HarfBuzz keeps no old size.
- Gate, `scripts/screenshot-gate.mjs:6840-6866`: `still()` waits only until scrolling stops, not until the zoom ends. `place()` then sets `will-change:transform`, `position:relative` and `top` on the app panel and moves the sheet scroller, possibly while the zoom is still running. On golden B, `place()` only does an instant window scroll. With `will-change` set, the end of the zoom no longer flips the stacking context, so the re-layout that normally fixes the text at rest never runs.
- Arithmetic: good = 6190 and bad = 6180 LayoutUnits (1/64 px at scale 3.82116). Every width is a whole LayoutUnit, so the "exactly 10/64 px" finding tells us nothing.

**1. Ranked hypotheses**

**H1 (0.45): stale glyph run.** The label is shaped once mid-zoom, at about 167 ms (k ≈ 0.9985, so an 18.69 px font). It is never re-laid out at rest, and a later style change resets the divisor to the rest value.
- Fits: two lenses independently reproduce 25.2705, and frame 10 is the only frame in the 18.69 window. It also fits "Right" never changing, the dependence on load and scroll mode, and golden B at 0/300 (no mid-zoom layout change).
- Fails: the fresh `<text>`, the re-attach and the font-size flip all stayed bad. By the code above, each of those must re-shape at rest. H1 survives only if those probes were confounded, for example measured before rest.

**H2 (0.2): stale ancestor transform.** A PaintLayer transform stays at the frame-10 sample, so every new layout re-reads it.
- Fits: the persistence results (fresh text, re-attach, flip).
- Fails: `getComputedTextLength` would read about 25.308, `getScreenCTM().a` about 1.9078 rather than 1.91058, and "Right" would move too. It only fits if the builder measured width with `getBoundingClientRect`. That is unknown.

**H3 (0.15): per-tab font state per size.** Some cache hands the 18.72 px request an 18.69 px glyph run.
- Fits: the persistence results, and a fresh tab being good.
- Fails: I found no such path in 141. The HarfBuzz layer is verified clean, the 18.72 and 18.69 cache keys never collide, and pre-warm made it worse.

Dropped: history `pushState` (no mechanism), a GC-held Font object (no stale size is possible per key), and harness-only timing or diffing (it cannot produce this width).

**3. Fixes**

**H1 with `place()` as the trigger:** in the HT-7 block, `still()` also waits for the panel's animations to finish, plus 2 rAF. This is not a loosening: L3 is defined at rest, and the capture setup was running mid-zoom. The tap, golden B and the 0 px threshold stay the same. The supervisor rules on the gate change.

**H1 if E2 run B shows bad opens without `place()`, and H2:** an app fix in `src/slices/howto/zoom/ZoomHost.tsx` (`anim.onfinish`, line 122). On `anim.finished` plus 1 rAF, in one task:
1. Set the panel's transform to `scale(1)`, flush, remove it, flush. This refreshes the layer transform and forces a re-layout when the panel is not already a stacking context.
2. On each crop `<text>`, set `text-rendering: geometricPrecision`, flush, remove it, flush. This re-shapes the text at the rest scale whatever the stacking state.

No frame is painted in between, so both the motion and the pixels at rest match golden B.

**H3:** prevent the trigger. Give the crop `<text>` `geometricPrecision` only while the enter animation runs, and remove it on finish or cancel. That sets the scaling factor to 1 (line 190), so no font is ever created at a mid-zoom scale. Trade-off: during the 240 ms the glyphs are drawn as scaled outlines, so the existing motion check must pass unchanged. If it fails, no fix meets every constraint. The least-bad option is to keep the gate red and send the owner and supervisor the E1 data, with one option: move the test browser to a Chromium where `SvgIgnoreOuterTransforms` is on, which removes the cause. Golden B would then have to pass L3 again on that build.

**4. Confidence and unknowns**
- About 0.75 that the root is the zoom's mid-animation scale getting into the SVG font size in Chromium 141. About 0.45 for H1 specifically.
- Still unknown:
  - what lays out the text at about 167 ms, and why it is always frame 10;
  - whether the builder's width and CTM came from `getComputedTextLength` and `getScreenCTM`;
  - whether the single-browser loops used `place()`;
  - whether the persistence probes ran at rest.
